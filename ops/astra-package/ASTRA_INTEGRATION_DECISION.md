# Architecture decision: A vs B

**A — WF 05**: Yuri provided `05-Messe-Hub-Daten-fuers-Dashboard.json` with a `GET /messe-hub/daten` n8n webhook using Basic Auth, PostgreSQL queries and separate n8n Data Table for merge history. Adapting it would require a new published/secured n8n workflow, an additional upstream authentication path, credential management and removal of merge-history dependency. We did **not** import/activate it or use its Basic Auth. No global webhook was exposed.

**B — Gateway direct read-only Neon**: Existing authenticated Gateway session and same-origin authorization; one server-only PostgreSQL driver (`pg`), one static SELECT-only function with a bounded result and narrow EXECUTE grant after explicit review. No new service or n8n workflow. Existing form, WF-A–D and nginx unchanged. **Chosen**, subject to exact baseline/DDL review. If approved database permissions cannot be supplied, leave Dashboard disabled and mark NO-GO rather than falling back to public n8n.

**Risks accepted for review, not deployment:** existing `trade_fair_app` may not be an appropriate read role for full AI result details. A SECURITY DEFINER function grants additional *read capability* even without table SELECT; security reviewer must select an approved existing role or authorize a dedicated scoped role. Actual Neon DDL is missing some metadata; no live schema alterations are authorized by packaging alone. The Gateway Docker build needs to install the sole new runtime dependency. Gate F3B must already route `/dashboard` and `/api/dashboard` to the Gateway; no proxy change is included.
